# 五分钟性能目标

## 定义

对于输入时长不超过 300 秒的视频，CineFlow 的目标是尽可能在任务提交后的 300 秒内交付成片。

这不是硬 SLA，也不是强制超时：

- 预测超过 300 秒仍可接收；
- 没有空闲槽位时进入有界队列；
- Worker 未预热会产生警告，但不会仅因此拒绝；
- 运行到 300 秒不会取消任何 Provider 请求；
- 超过目标后继续执行，直到成功、降级成功或真实失败；
- 最终通过 `target_exceeded` 记录是否达到目标。

公网上传时间不计入该指标。现有客户端完成 OSS 上传和可选字幕消除后，才调用本服务。

## 哪些情况仍会拒绝

拒绝只用于无法正常执行或明显违反约束的任务：

- 视频超过 5 分钟；
- 输入文件超过配置上限；
- 输入编码完全不支持；
- 必需 Provider 没有任何健康的首选或后备路径；
- 预计费用超过请求中的 `max_cost_cny`；
- 请求参数不合法。

“预计会慢”“当前槽位繁忙”“Worker 是冷的”都不再单独构成拒绝理由。

## 性能检查点

下列值只用于监控和优化，不会触发取消：

| 阶段 | 目标检查点（任务接受后） |
|---|---:|
| ASR | 60 秒 |
| 媒体准备 | 130 秒 |
| 多模态人物 + DeepSeek 翻译 | 170 秒 |
| Azure TTS | 245 秒 |
| 最终合成 | 290 秒 |
| 整体目标 | 300 秒 |

阶段超过检查点时发送 `performance_warning` 事件，流水线继续运行。

## 并发与排队

`max_inflight_jobs` 控制同时运行的任务数。额外任务进入内存队列，并通过以下字段可见：

```json
{
  "inflight": 2,
  "queued": 1,
  "max_inflight": 2,
  "available": 0
}
```

生产环境应把队列和任务状态迁移到 Redis/Postgres，避免进程重启丢失。

## Provider 健康和预热

- `healthy=false` 且没有后备路径：拒绝；
- `healthy=true, warm=false`：接受并提示可能错过目标；
- 首选端点失败：调用后备端点；
- 部署策略：阿里云优先，火山引擎后备；
- DeepSeek 翻译和 Azure TTS 按已确认方案保留。

## 费用门禁

费用预算仍是硬门禁，因为它与用户明确授权有关。估算包含本服务负责的：

- ASR；
- DeepSeek 翻译；
- Azure TTS；
- 多模态 GPU；
- 可选声伴分离；
- 最终合成。

现有 OSS 上传和字幕消除属于上游流程，不在本服务报价中重复计算。

## 上线验收

真实生产目标应使用代表性视频矩阵统计：

- p50；
- p90；
- p95；
- `target_exceeded` 比例；
- 各阶段耗时；
- 人物归因准确率；
- 单任务实际成本。

第一阶段目标是提高 300 秒内成功率，而不是通过拒单或强制超时制造虚假的达标率。
